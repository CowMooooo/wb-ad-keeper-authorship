# Decision Log — WB Ad Keeper

## 2026-06-07 — v0.1

### Контекст

Первичная задача: сделать собственную систему управления рекламой WB, чтобы не зависеть от внешних сервисов, не платить за чужую логику и иметь инструмент, который работает по правилам владельца.

### Принятые решения

1. Делать свой self-hosted сервис.
2. Использовать официальный WB Promotion API.
3. Не парсить кабинет WB.
4. Не строить real-time SERP-парсер в первой версии.
5. Работать по `normQuery` / поисковым кластерам.
6. Делать regex-классификацию, потому что владелец проекта может заранее дать базу целевых и нецелевых фраз.
7. Ввести actions-очередь вместо немедленных изменений.
8. Держать `ALLOW_APPLY=false` по умолчанию.
9. Делать биддер по средней позиции `avgPos`, а не по живой позиции в выдаче.

### Почему так

Главная цель v0.1 — быстро получить безопасный внутренний инструмент: собрать данные, классифицировать фразы, предложить действия, залогировать решения.

## 2026-06-07 — переход к v0.2

### Новая проблема

Рекламная атрибуция WB не всегда отражает фактический эффект рекламы. Реклама может увеличить общие заказы товара, даже если WB не записал эти заказы в рекламные `orders`.

### Новая гипотеза

Нужен слой, который накладывает закупленный рекламный трафик на фактические заказы магазина:

```text
ad traffic → total orders
```

В разрезах:

```text
магазин → группа товаров → nmId
```

### Принятые решения v0.2

1. Добавить отдельный analytics layer.
2. Брать рекламный трафик из WB Promotion API `/adv/v3/fullstats`.
3. Брать все заказы из WB Statistics API `/api/v1/supplier/orders`.
4. Сохранять сырые ответы в БД.
5. Строить агрегаты у себя, а не через Excel/VPR.
6. Главный ключ сводки: `date + nmId`.
7. Группы товаров хранить в собственной БД.
8. Добавить системные логи `system_logs`.
9. Добавить страницу `/analytics`.
10. Добавить endpoint `/api/analytics/metrics`.

### Почему не Excel/VPR

Excel/VPR не подходит как основа продукта:

- ручной труд;
- ошибки выгрузок;
- некорректные рекламные таблицы в кабинете;
- плохая история;
- нет автоматического backfill;
- нет групп товаров;
- нет единого источника истины.

### Ограничение идеи

`Traffic vs Orders` показывает связь во времени, но не доказывает причинность. Это правильный управленческий инструмент, но не строгая модель атрибуции. Для доказательства причинности нужны контрольные тесты.
