# Порядок публикации и усиления доказательств

## 1. Перед публикацией

1. Проверить, что публикация выполняется из нужного GitHub-аккаунта. Полное имя автора публиковать не требуется.
2. Проверить, что в папке нет `.env`, токенов, баз данных, исходных отчётов и сведений конкретных кабинетов.
3. Не добавлять закрытые ZIP-архивы версий: часть старых архивов содержит локальную базу данных.
4. Не публиковать исходный каталог WB Ad Keeper целиком.
5. Проверить `git status` и список файлов перед каждым коммитом.

## 2. Публичный репозиторий

Рекомендуемое имя:

```text
wb-ad-keeper-authorship
```

Режим:

```text
Public
```

Назначение: публичная фиксация продукта, архитектуры, хронологии и контрольных сумм без раскрытия исходного кода.

## 3. Первый коммит

Коммит создаётся текущей датой. Нельзя подменять его дату июнем.

Рекомендуемое сообщение:

```text
Публичная фиксация происхождения и архитектуры WB Ad Keeper
```

После публикации нужно записать хеш коммита в декларацию.

Git-коммит следует создавать с GitHub-адресом `noreply`, чтобы не раскрывать обычную электронную почту. Для современных аккаунтов GitHub использует формат:

```text
ID+USERNAME@users.noreply.github.com
```

## 4. Публичный релиз

После первого коммита создать GitHub Release:

```text
v0.7.2-prior-art-record
```

Название:

```text
WB Ad Keeper — публичная фиксация ранее созданного продукта
```

В описание релиза включить:

- начало разработки: 7 июня 2026 года;
- публичная фиксация: 28 июля 2026 года;
- ссылку на декларацию;
- ссылку на хронологию;
- предупреждение, что исходный код не лицензируется и не распространяется.

## 5. Дополнительная внешняя фиксация

После появления публичной ссылки:

1. Сохранить URL репозитория и релиза.
2. Сделать PDF страницы релиза средствами браузера.
3. Передать URL в независимый веб-архив.
4. Сохранить уведомление GitHub о создании репозитория и релиза.
5. Сохранить переписку и материалы от 7–8 июня 2026 года в неизменном виде.
6. Не редактировать старые архивы; новые версии хранить отдельными файлами.

## 6. Закрытый репозиторий исходного кода

Создать второй репозиторий:

```text
wb-ad-keeper-private
```

Режим:

```text
Private
```

В него переносится санитарная копия исходников. Обязательные исключения:

```text
.env
.env.*
!.env.example
**/secrets/**
*.db
*.sqlite
*.sqlite3
*.zip
__pycache__/
*.pyc
.venv/
venv/
.DS_Store
```

Закрытый репозиторий нужен для последовательной истории разработки, но публичным доказательством даты является публичный репозиторий и его релизы.

## 7. Правило дальнейшей разработки

Каждое самостоятельное изменение оформляется отдельным коммитом:

```text
функция → тесты → описание → коммит → тег версии
```

Данные конкретной компании подключаются только через конфигурацию и никогда не смешиваются с ядром продукта.

## 8. Что реально доказывает GitHub

GitHub надёжно показывает, что определённый набор материалов был опубликован не позднее даты серверного коммита или релиза. Публикация 28 июля не доказывает автоматически создание в июне.

Для подтверждения более раннего происхождения используются опубликованные июньские документы, закрытые архивы с совпадающими SHA-256 и независимые материалы с временными отметками.
