# Архитектура универсальной панели продвижения

Дата фиксации текущего описания: 28 июля 2026 года.

Архитектура продолжает два ранее сформированных принципа автора: ассортиментная матрица листингов и категорий со сквозной историей по дням и неделям, возникшая в 2021 году, и единый график трафика карточки, корзин и заказов, сформулированный и применявшийся в 2024 году.

## 1. Продуктовый примитив

WB Ad Keeper строится вокруг одной понятной строки:

```text
артикул продавца + фраза продвижения + период = показатели + решение
```

Если выбрано несколько кабинетов, абсолютные показатели суммируются по каноническому артикулу продавца. При необходимости пользователь раскрывает строку и видит вклад каждого кабинета.

Для пользователя поисковый текст и рекламный кластер являются одной сущностью — фразой продвижения. Система может хранить техническую метку источника, но не заставляет пользователя управлять двумя отдельными таблицами.

## 2. Универсальный конвейер

```text
источники данных
  → безопасная загрузка с соблюдением лимитов
    → локальная история
      → нормализация кабинетов, артикулов и фраз
        → дневные факты
          → агрегация по дням, неделям и месяцам
            → аналитика эффективности
              → предлагаемые действия
                → журнал решений
                  → отдельное подтверждение записи
```

## 3. Источники данных

Платформа должна уметь подключать любое количество источников:

- стандартные API Wildberries;
- подписка «Джем»;
- API продвижения Wildberries;
- ручные выгрузки через окно Finder;
- кабинеты Ozon и Яндекс Маркета через отдельные адаптеры;
- внешние данные о нише, конкурентах и ценовом сегменте;
- себестоимость, комиссии и экономика товара.

Подключение нового источника не должно менять аналитическое ядро. Адаптер приводит данные к внутренним сущностям продукта.

## 4. Внутренние сущности

### Кабинет

- маркетплейс;
- юридическое лицо;
- пользовательское название;
- доступные категории API;
- состояние подключения;
- отдельный ограничитель запросов.

### Товар

- кабинет;
- артикул маркетплейса;
- артикул продавца;
- наименование;
- предмет и группа;
- статус активности.

Артикул маркетплейса остаётся техническим ключом API. Артикул продавца используется для объединения товара между кабинетами.

### Фраза продвижения

- исходный текст;
- нормализованный текст;
- артикул;
- дата;
- технический источник;
- показатели спроса;
- показатели позиции;
- показатели воронки;
- рекламные показатели;
- затраты;
- статус и предлагаемое действие.

### Дневные показатели

- показы и видимость;
- позиция;
- переходы и клики;
- корзины;
- заказы и заказанные товары;
- выкупы, если источник их предоставляет;
- рекламный расход;
- остатки FBO и FBS;
- цена и скидка;
- маржинальный доход.

### Решение

- оставить;
- наблюдать;
- усилить;
- снизить ставку;
- не повышать ставку;
- исключить;
- защитить;
- проверить вручную.

На первом этапе все решения только предлагаются. Автоматическая запись в кабинет отделена двойным предохранителем и журналируется.

## 5. Представления панели

### Портфель

Показывает группы и артикулы, которые имеет смысл продвигать с учётом:

- наличия;
- спроса;
- конверсии;
- позиции;
- рекламной эффективности;
- маржинальной прибыли.

### Артикул и фразы

Одна строка на каждую связку `артикул + фраза`:

- частота;
- позиция;
- показы;
- клики;
- корзины;
- заказы;
- расход;
- цена заказа;
- ожидаемая маржинальная прибыль;
- предлагаемое действие.

### История

Динамика по дням, неделям и месяцам:

- остатки;
- воронка;
- продажи;
- реклама;
- позиции;
- действия системы.

### Управление кабинетами

Пользователь выбирает:

- один или несколько кабинетов;
- один или несколько маркетплейсов;
- период;
- товар, группу или весь ассортимент.

При выборе нескольких кабинетов основная строка показывает сумму. Детализация по кабинетам открывается по запросу.

## 7. Универсальное развитие продукта

Следующие функции являются развитием общего продукта, а не логикой конкретного ассортимента:

- несколько кабинетов и маркетплейсов;
- единая матрица по артикулу продавца;
- загрузка запросов и заказов из «Джема»;
- ручной импорт файлов;
- исторические остатки;
- полная экономика товара;
- прогноз продаж;
- выбор артикулов с максимальной ожидаемой маржинальной прибылью;
- интеграция с централизованным управлением рекламой.

Новые функции должны разрабатываться без жёстко зашитых названий компаний, кабинетов, юридических лиц и ассортиментов. Любая конкретная компания подключается как конфигурация.

## 8. Граница точности

Панель должна отделять:

- фактические поля, которые вернул источник;
- нормализованные показатели;
- вычисленные KPI;
- прогнозы и оценки;
- решения пользователя;
- действия, реально отправленные в кабинет.

Это позволяет расширять продукт без выдачи расчётной оценки за первичный факт.
